### Syntheticsally generating traces

Top mistake: people ask their coding agent, "generate a handful of questions for me, and I"ll run this through the
agent". Not great, because the questions end up being pretty generic. "Where is my order?", "Can you check the status?"
etc. These are not obviously wrong, but there is so little diversity.

We know that if we're building e-commerce support bot, ppl will ask for more than just status, it will be complex.
Store policy, refunds, what should I buy, etc.

Key idea: Use the agent to generate *scenarios*. Don't ask agent to generate questions specifically.

Scenario: planned user request, plus its expected result.

Steps:

* Define dimensions of variation (role, intent, order state...)
* Sample tuples and generate requests
* Review: remove duplicates and unrealistic requests
* Compute expected outcomes from the database
* Validate and run through agent
* Traced support requests

#### Step 1: define dimensions of variation
Dimension: a named source of variation, read from specification. Role, intent, record involved, applicable policy,
tools needed, difficulty, user style

The choice of dimensions is to find things that will break the application. Come with some hypotheses that ground
the dimensions. So, be a little adversarial. To do that, pay attention to what smells the application would have.
Ask users, what breaks, at a high level.

Another way of coming up with dimensions is to look at the tools the agents have access to; search API, etc. So what
are the places it might break when using tools.

Rule of thumb: three dimensions to start with, maybe add some more.

Go through at least ten dimensions, depending on whether the dimension will allow it.

There's a spectrum of effort: on one side, ask the agent to do it all. On the other end of the spectrum, every extreme,
every source of data, every cross product. You want to be somewhere in the middle, as there is a cost-benefit to more
energy spent, diminishing returns.

From a tuple, we generate a request from the user. Request: message a user with that tuple they would send. The model
will generate it from the tuple.

These messages are going to be inputs to the system. From there, you feed the message through the system/agent and then
you view the trace. The trace is not generated by the synthetic process, only the tuple-message is.

You can ask the agent to create more combinations, with a few hand-written tuples as examples.

Separate requests into two sets: coverage set and challenge set.

Coverage set: to cover variation you know exists. Challenge set: we know about some failures, we will try to 
systematically induce them. Put pressure on permissions, policy boundaries, damaged records.

What if you're not a domain expert? LOOK AT THE DATA. You can take real user data and slightly tweak it.

One dimension you can have: follow-up requests. In the tuple, you can have follow-up things written in.

It doesn't matter as much how many examples you use, but what quality they are. Be adversarial. Shreya used to say 100
questions, but as agents have gotten more sophisticated, she's expanded to the 150-75 split.

Review the resusts:
Independent critic pass for repetetive or template-like language. Unrealistic wording, impossible combinations. Person
reads questions before application runs.

Compute synthetic outcomes:
You can pre-fetch relevant data, and reason about the expected result. Often there is no single right answer, but
having some aspect of the right answer is helpful. It helps to know where the source data was.

Validate/run through the agent:
Validate the file: shape, duplicates, group counts
Run request through agent
Since agent is instrumented, each run is run through Langfuse, so traces are computed.

Expected outcome:
The piece of data in the database, or in policy documents, the data quality table. So there is no
single right answer. It's just the tool path and the data source referenced that matters here.

Looking at traces is tedious, so anything you can do at this stage will accelerate you.

Make sure that the combination of dimension data in the tuples make sense.

Would you follow this for a data agent or deep research agent? YES, this process is even more important in this context.

Expected outcome is coming from a mix of LLM and programmatic and human. You can ask people on the team what is most
common. There is no right way necessarily.

How is expected outcome used? Shreya puts it in her error analysis dashboard. When reviewing traces, you can see if
you got the right sources.

They used to do this by hand, they're now using agents.

This is really about partial expected outcome. You absolutely should keep some data alongside the trace so it can be
reviewed. Expected outcome is partial expected outcome, and anything that will help you review. You can tell the agent
what is supposed to be review, but ground truth can be something you keep in the expected outcome. Expected outcome
could be any data you expect to be used. It's only used for you when you go to review.

It's important because you might have something you know you need, you want to be able to reference it when you review.

Is it good to start offline eval using existing benchmark dataset similar to data or use case? Hamel says naw, because
these are synthetic. You want to get into your own data as soon as possible, because benchmark data set will just waste
your time. You could ask, who made it, does it match data to be used? Usually not likely.

Error analysis:
We just created trace data set
Second step: read and open code traces. (Open coding, axial coding (grouped failure modes), some sort of qualitative 
analysis.)

Given a trace, what are the issues? Read each trace top to bottom. User messages, tool calls, tool results, final 
answer. Stop at the first step the agent did something wrong. Write a note in your own words: what happened, what should
have happened. Review as many traces as possible.

Trace review is Hamel's favorite part of evals. The most magical part of the whole eval process.

Vibe-coding a custom UI for open coding:

Ask codoing agent to build a trace review interface over pilot traces.
Some parts of the interface spec:
* Conversation messages in order
* Tool calls beside their results
* Annotation
* < something else I missed>

In the beginning, spend 5+ minutes on each trace. You'll get faster.

Why make your own interface instead of Langfuse's? 1. It's easy to see everything on one screen. 2. The application
you're building is something specific. So the review tool should be make specific to the domain. For example, maybe
you're building an email related application. You might want your tool to view the generated email, for example.

Error anlysis:
Open coding (what is this?): User input: "I need refund for lamp, it broke after two days." Go into tool calls, look
at data used for any inconsistencies. 

What happened here as Shreya looked at the trace is that the agent checked a lot on policies, sent a lot of messages
to the user about policy, etc. The user then looked a bit annoyed. So this is a fail.

Put your product hat on. Is this a good performance?

Shreya likes to think about: Factual/logical errors vs. user experience errors. In this case, the user is seeing
a lot of back and forth that is really annoying.

Shreya used the vibe-coded interface's feature of highlighting a word and writing a note on it.

Open coding can be really useful because you might not even get into an eval, you can be like, okay this sucks. 

No one looks at traces. When you look at a trace, you'll learn more about the product than anyone else.

A big problem with agents is that they often make conflicts.

First major problem is the one that's most important to focus on, but you will want to see a lot of traces.

If you've never done open coding before, stop at the first failure. As you get better at error analysis, you can do more
over time. You're trying to increase the failure modes you find over time. Can't expect to find every failure mode from
day one.

Why can't Claude do this? Because it lacks context I think. Agent can cause logical error--issue in the trace. But it
can't catch things that only you know. This process is getting the knowledge/taste in your head into codified cases.

As far as this taking a lot of time, you will get better over time. They will also give better techniques. Making tools
like the vibe coded interface will help a lot. 

Open coding is writing notes on the side of the traces. Trace review is just looking at traces. "Open coding" is used
in qualitative research.
